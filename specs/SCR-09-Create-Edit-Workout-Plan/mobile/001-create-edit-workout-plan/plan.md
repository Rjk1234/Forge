# Implementation Plan: SCR-09 Create / Edit Workout Plan

**Branch**: `001-create-edit-workout-plan` | **Date**: 2026-09-17 | **Spec**: [spec.md](spec.md)

**Input**: [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md)

## Summary

SCR-09 delivers a dual-mode (Create / Edit) screen for building and updating workout plans entirely offline via Drift. The screen is pushed (slide-left) from SCR-08 (create mode via "+" FAB / empty-state CTA) and from SCR-10 (edit mode via plan detail). The implementation extends the existing `workout_plan` feature with new domain entities, two new use cases, a new Bloc, and a new presentation screen. No new packages are required — `uuid`, `drift`, `flutter_bloc`, `go_router`, `fpdart`, and `equatable` are all already in `pubspec.yaml`.

## Key Design Decisions

### Decision 1 — WorkoutPlanDetail as a separate domain entity

`WorkoutPlan` (the existing entity) is a list-view projection carrying only `id`, `name`, `exerciseCount`, `createdAt`. For the create/edit form, the full exercise list with all target fields is required. A separate `WorkoutPlanDetail` entity is introduced rather than expanding `WorkoutPlan`, keeping the list-view entity lean (no unnecessary data loaded when only the count is needed).

### Decision 2 — Picker returns Exercise object

`ExerciseCatalogueScreen._onAddExercise` is updated to call `context.pop(exercises[i])` rather than `context.pop(exercises[i].id)`. This eliminates the need for a `GetExerciseByIdUseCase` and removes an extra database read per added exercise. The existing `_onAddExercise` signature receives `String exerciseId`; it will become `void _onAddExercise(Exercise exercise)`. The picker banner and filter chips are unaffected.

### Decision 3 — PlanExerciseFormEntry in Application layer

The form's in-memory exercise list uses a mutable `PlanExerciseFormEntry` value object in the Bloc state's `List<PlanExerciseFormEntry>`. This is a deliberate Application-layer concept — it is not a Domain entity and never touches Drift. On save, the Bloc uses `WorkoutPlanMapper.formEntryToPlanExercise(entry)` to convert each entry into a `PlanExercise` domain entity before calling `SaveWorkoutPlanUseCase`.

### Decision 4 — Validation errors stored per-field in Bloc state

The Bloc state `CreateEditPlanReady` carries `String? nameValidationError` and `Map<int, List<String>> exerciseErrors`. On `SaveRequested`, the Bloc runs validation and emits a new `CreateEditPlanReady` state with errors populated (canSave becomes false). On field-change events, the relevant error is cleared immediately without re-running full validation — this satisfies FR-012 ("clear immediately once corrected") without an expensive full-validation pass on every keystroke.

### Decision 5 — PopScope pattern for back guard

`CreateEditWorkoutPlanScreen` wraps its `Scaffold` in `PopScope(canPop: false, onPopInvokedWithResult: ...)`. The back icon in the `AppBar` calls `_onBackRequested()` (a method on the state class) rather than `context.pop()`. During `CreateEditPlanSaving`, `_onBackRequested` returns early. When the form is clean (`!isDirty`), `_onBackRequested` calls `context.pop()`. When dirty, it shows the `DiscardDialog` via `showDialog`.

## Post-Constitution Check (after Phase 1 design)

All Phase 1 design decisions (entities, mapper, use cases, Bloc, routing) are consistent with ForgeApp's constitution:
- No network surface introduced
- Drift `workout_plans` table is the sole persistence target; `exercises` table is read-only (for reference validation)
- No new Drift table needed (all records already exist)
- Clean Architecture layer boundaries preserved: domain entities import only `equatable`; data layer imports `drift` and domain; application imports domain only; presentation imports application and domain
- No Cubit; no second router; no second DI mechanism
- All 6 screen states are modelled in Bloc states (FR spec: Initial, Loading, Ready, Saving, Saved, LoadError, SaveFailure — 7 states for robustness)
