# Implementation Plan: Delete Plan Confirmation (SCR-11)

**Branch**: `001-delete-plan-confirmation` | **Date**: 2026-09-19 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/SCR-11-Delete-Plan-Confirmation/mobile/001-delete-plan-confirmation/spec.md`

## Summary

SCR-11 delivers a three-state modal confirmation dialog for plan deletion. The user triggers it from SCR-10 (Plan Detail) via the Delete icon. The dialog confirms intent (state 1), executes the Drift deletion (state 2 — loading, all input locked), and surfaces a retry path on failure (state 3). On success it navigates to SCR-08 (Plans List) without retaining SCR-10 in the stack.

New components: `DeletePlanBloc` (Confirmation / Deleting / Failure states), `DeletePlanDialog` widget, `DeleteWorkoutPlanUseCase`. Data-layer additions: `deletePlan` on `WorkoutPlanRepository` and `WorkoutPlanRepositoryImpl`; `deleteEntriesForPlan` on `ScheduleLocalDataSource`. Token addition: `AppColors.onDanger`. SCR-10's `_onDelete` is updated from `context.push(deleteRoute)` to `showDialog()`.

## Technical Context

**Language/Version**: Dart 3 / Flutter 3.x (stable)

**Primary Dependencies**: `flutter_bloc` (Bloc only), `go_router`, `GetIt`, `fpdart`, `equatable`, `drift` — all existing in `pubspec.yaml`; no new packages

**Testing**: `flutter_test` — plain fake implementations (no `mocktail` or `bloc_test`)

**Target Platform**: iOS + Android phones (dark theme, phone-sized layout)

**Performance Goals**: Dialog renders within one frame of trigger; Drift write completes well within human perception

**Constraints**: Fully offline — zero network calls; single dark theme; Bloc not Cubit; go_router only; no new dependencies without ADR; `WorkoutPlanRepository.deletePlan` must be sequential (schedules first, then plan) to minimise orphan risk

`dangerBg` (`#2A1F1F`) and `dangerBorder` (`#5C3A3A`) already exist. All hardcoded hex values used in the dialog MUST come from these tokens — no inline hex in widget code.

### `ScheduleLocalDataSource.deleteEntriesForPlan`

New method added to the abstract class and `ScheduleLocalDataSourceImpl`:

```
deleteEntriesForPlan(String planId):
  select all `schedule_entries` rows (max 7)
  for each row where plan_id == planId:
    await delete the row for entry.weekday
```

Called by `WorkoutPlanRepositoryImpl.deletePlan` before deleting the plan entry.

### `WorkoutPlanRepositoryImpl.deletePlan`

Sequential delete: schedule entries first, then the plan. If either step throws, the exception surfaces as `Left(CacheException(...))`.

```
deletePlan(planId):
  try:
    await scheduleDataSource.deleteEntriesForPlan(planId)  // step 1
    await dataSource.deletePlan(planId)                    // step 2
    return Right(null)
  catch e:
    return Left(CacheException(message: "Couldn't delete the plan", originalException: e))
```

Constructor updated: `WorkoutPlanRepositoryImpl({required this.dataSource, required this.scheduleDataSource})`.

**Rationale for order (schedules first)**: If step 2 fails, the plan still exists — a consistent state. If step 1 fails, the plan still exists and schedule entries are intact — also consistent. The only gap is if step 1 succeeds and step 2 fails (plan exists, no schedules for it) — this surfaces as a delete failure so the user retries; the plan entry and schedules can be re-synced by Retry. See `research.md` for full analysis.

### `DeletePlanBloc`

```
States (sealed):
  DeletePlanConfirmation                    — initial: show dialog, both buttons enabled
  DeletePlanDeleting                        — Drift write in flight; Cancel disabled; spinner shown
  DeletePlanSuccess                         — Drift write succeeded; dialog pops with true
  DeletePlanFailure({required String message}) — write failed; inline error shown; Retry enabled

Events (sealed):
  DeletePlanConfirmed({required String planId})  — user tapped Delete (or Retry from failure state)

Handlers:
  on<DeletePlanConfirmed>(_onConfirmed):
    emit(DeletePlanDeleting())
    result = await deleteWorkoutPlan(event.planId)
    fold:
      Left(failure) → emit(DeletePlanFailure(message: failure.message))
      Right(_)      → emit(DeletePlanSuccess())
```

Registered as `registerFactory<DeletePlanBloc>` — fresh instance per dialog open.

### `DeletePlanDialog`

`StatelessWidget`. Caller (SCR-10 `_onDelete`) provides a `BlocProvider` wrapper.

```dart
class DeletePlanDialog extends StatelessWidget {
  const DeletePlanDialog({required this.planId, required this.planName, super.key});
  final String planId;
  final String planName;
}
```

Uses `BlocConsumer`:
- **`listener`**: On `DeletePlanSuccess` → `Navigator.pop(context, true)` (returns true to caller)
- **`builder`**: Switches on state to render the correct action row

**Dialog structure** (const where possible):
1. Full-screen scrim (`barrierColor: AppColors.scrimBarrier`, `barrierDismissible: true` — scrim tap acts as Cancel in Confirmation/Failure states; `PopScope(canPop: false)` blocks it during Deleting)
2. Centred card: `AppColors.card` fill, `AppColors.border` border, 18px radius, 24×20px padding
3. Trash icon (`AppColors.danger`, 36×36px)
4. Title: "Delete this workout plan?" — `textTheme.titleMedium`, `colorScheme.onSurface`
5. Subtitle: `""$planName" and its schedule assignments will be removed. Past workout sessions using this plan are unaffected."` — `textTheme.bodySmall`, `AppColors.textMuted`
6. [Delete Failure only] `InlineDialogError` widget with error message
7. Action row (two `Expanded` buttons, gap 10px)

**Button variants by state:**

| State | Left button | Right button |
|-------|-------------|-------------|
| Confirmation | Cancel (enabled, `AppColors.cardAlt`) | Delete (enabled, `AppColors.danger` fill, `AppColors.onDanger` text) |
| Deleting | Cancel (disabled, opacity 0.5) | Deleting… (spinner + text, `AppColors.danger` fill, opacity 0.85) |
| Failure | Cancel (enabled, restored) | Retry (`AppColors.lime` fill, `AppColors.onLime` text) |

**Cancel taps**: Call `Navigator.pop(context, false)` directly — no Bloc event.
**Delete tap**: Dispatches `DeletePlanConfirmed(planId: planId)`.
**Retry tap**: Dispatches `DeletePlanConfirmed(planId: planId)` (same event — re-attempts the write).

**Back gesture / scrim tap**: The `showDialog` call from SCR-10 uses `barrierDismissible: true` — barrier taps during Confirmation and Failure states pop the dialog with `null`, which `_onDelete`'s `if (deleted == true)` guard treats as Cancel. The dialog wraps its content in `PopScope(canPop: state is! DeletePlanDeleting)` which blocks both Android system back and barrier-tap pops during Deleting state. In Confirmation and Failure states `canPop: true` (equivalent to Cancel).

### `PlanDetailScreen._onDelete` (modified)

```dart
Future<void> _onDelete(String planName) async {
  final deleted = await showDialog<bool>(
    context: context,
    barrierDismissible: true,
    barrierColor: AppColors.scrimBarrier,
    builder: (_) => BlocProvider(
      create: (_) => getIt<DeletePlanBloc>(),
      child: DeletePlanDialog(planId: widget.planId, planName: planName),
    ),
  );
  if (!mounted) return;
  if (deleted == true) {
    context.go('/plans');
  } else {
    _reload();
  }
}
```

The `planName` is sourced from the `PlanDetailLoaded` state at the time of the tap. The `_buildLoaded` method provides a closure that captures `plan.name`.
