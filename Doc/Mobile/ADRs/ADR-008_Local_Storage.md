# ADR-008 Local Storage

Version: 2.0 (ForgeApp)

Status: Accepted

---

> **Changelog**
> - **2.0 (2026-09-08):** Written for ForgeApp. Drift (typed SQLite) is the **sole source of truth**
>   for all application data, with no restriction to "preferences only" and no business/operational
>   data prohibited from local persistence — because there is no backend at all (SDS §2.2–2.3, §6).
>   The upload-queue/media-draft exception carve-out is N/A (no media capture, no background upload
>   in ForgeApp), and so is the Secure Storage cross-reference (no tokens exist to secure).

---

## Context

ForgeApp is fully offline. The local database is not a cache or a preferences store sitting alongside
a backend — it **is** the backend (SDS §2.2: "there is no remote source — the Drift database is the
source of truth"). Every business entity the app has (SDS §6.1) lives in it:

```text
SDS-DATA-1  Local App Access State (lock flag)
SDS-DATA-2  User Profile
SDS-DATA-3  Exercise (seeded catalogue, read-only from client)
SDS-DATA-4  Workout Plan
SDS-DATA-5  Workout Schedule
SDS-DATA-6  Workout Session (completed records)
SDS-DATA-7  Derived Statistics (computed from SDS-DATA-6, not separately persisted unless caching
            is later justified for performance)
```

The application requires a maintainable, type-safe local storage solution capable of holding all of
the above, including the parent/child relationships between them (a plan owns ordered exercises; a
session owns ordered exercises, which own ordered sets).

---

## Decision

The application shall use `Drift` (typed SQLite, code generated by `drift_dev`) as its sole
persistent data store for all business data listed above. The only exception is the theme
preference, the single device-level setting, which stays in `shared_preferences`. All Drift access
must be abstracted behind repositories and local data sources — no feature, Bloc, or use case
touches the database directly.

---

## Storage Architecture

```text
Feature
↓
Repository
↓
Local Data Source
↓
AppDatabase (Drift)
```

Feature modules must never access the database directly.

---

## Schema

One `AppDatabase` (`lib/core/database/app_database.dart`) owns the schema. The database file
(`forge.sqlite`) lives in the application documents directory (ADR-031). `schemaVersion` starts at
1 and is incremented with a Drift step-by-step migration for every later schema change. Foreign keys
are enabled.

```text
user_profiles       — SDS-DATA-2, single row (id fixed to 0)
exercises           — SDS-DATA-3, seeded at launch, read-only from the client thereafter
workout_plans       — SDS-DATA-4
plan_exercises      — ordered exercises of a plan (FK → workout_plans ON DELETE CASCADE,
                      FK → exercises ON DELETE RESTRICT)
schedule_entries    — SDS-DATA-5, one row per weekday (primary key = weekday, FK → workout_plans
                      ON DELETE CASCADE)
workout_sessions    — SDS-DATA-6
session_exercises   — ordered exercises of a session (FK → workout_sessions, ON DELETE CASCADE)
actual_sets         — ordered sets of a session exercise (FK → session_exercises, ON DELETE CASCADE)
(app lock state)    — SDS-DATA-1, in-memory (see ADR-001 / SDS-COMP-1)
```

Design rules:

- Child rows carry an explicit `position` so exercise and set order is preserved.
- `workout_sessions` stores the plan id and plan name as a **snapshot** and has no foreign key to
  `workout_plans` (nor `session_exercises.exercise_id` to `exercises`): deleting a plan must never
  alter workout history. Deleting a plan removes its schedule entries through the cascade.
- A plan can only reference exercises that exist: `plan_exercises.exercise_id` is a foreign key with
  RESTRICT, and the catalogue is synchronised by **upsert** at launch (an exercise that has left the
  seed is removed only while no plan uses it).
- Value rules are enforced twice — in the domain validators (`PlanValidator`, `SessionValidator`,
  shared `WorkoutValueRules`) and by CHECK constraints: non-blank plan name, sets and repetitions at
  least 1, weight greater than 0 and finite, durations at least 1 second (rest and session duration
  at least 0), weekday 1–7, all within `WorkoutLimits`.
- Enums (e.g. exercise type) are stored as text.
- Writes that touch more than one table (saving a plan, saving a session, replacing the exercise
  catalogue) run inside a single transaction.

---

## Allowed Usage

Everything the app persists: profile, exercise catalogue (seeded, read-only), workout plans,
schedule entries and completed workout sessions. There is no "business data must not be persisted"
rule here — the opposite is true: nothing the app needs survives a restart unless it is in the
database. The theme preference alone lives in `shared_preferences`.

---

## Not Allowed

- No secrets exist to protect (static local login is a hardcoded string comparison, not a stored
  credential — SDS Appendix B) — there is nothing that would ever need Secure Storage.
- No binary media (photos, voice notes) — ForgeApp captures none.
- No cross-feature direct table access — a feature accesses another feature's data only through
  that feature's repository interface (e.g. `schedule` reads plan names through the plan
  repository, never by querying `workout_plans` itself).

---

## Data Ownership

Each feature owns its tables and exposes access only through its repository interface. Features
must not read or modify another feature's tables directly.

---

## Preference Lifecycle

The theme preference is the only device-level setting; it survives across app restarts (there is
no "logout clears preferences" concept — logout only re-locks the app, per SDS-COMP-14, it does
not clear any stored data).

---

## Storage Principles

- Storage access must be asynchronous.
- Storage records (the data layer's `*Record` classes, populated from Drift rows) must remain
  separate from domain entities; a mapper converts between them at the repository boundary.
- Storage implementation must remain replaceable (e.g. swappable for an in-memory Drift database
  or a fake data source in tests).
- Business logic must not reside in storage records or table definitions.
- Schema changes require a `schemaVersion` bump and a tested migration step.

---

## Prohibited

- Direct database usage in UI, Blocs, or Use Cases
- Cross-feature storage access
- Any network-backed cache concept (there is nothing to cache from)

---

## Alternatives Considered

### SharedPreferences

Rejected for business data — insufficient structure for entities with relationships (a plan
referencing exercises, a schedule entry referencing a plan). Retained for the single theme
preference.

### Raw `sqflite`

Rejected — untyped SQL strings and hand-written result mapping; Drift provides the same SQLite
engine with compile-time-checked tables, queries and migrations.

### Isar

Rejected to keep a single, well-understood relational storage mechanism aligned with the SDS.

---

## Consequences

### Positive

- Single persistence mechanism; no cache-invalidation problem exists because there is no remote
  source to invalidate against
- Relational integrity (foreign keys, transactions) for plans, schedule and session history
- Type-safe, generated table and query code; in-memory databases make data-layer tests fast and
  realistic

### Negative

- All data-loss risk is local — there is no server copy to recover from if the database file is
  corrupted; SDS-ERR-5/6 (read/write failure handling) is the only mitigation, not a backup/sync
  layer
- Generated code (`*.g.dart`) must be regenerated with `build_runner` after schema changes
