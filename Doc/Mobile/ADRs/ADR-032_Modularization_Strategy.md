## Context

ForgeApp is built using Clean Architecture with Feature-First organization (ADR-001). As the
codebase grows across its 9 features, a modularization strategy prevents shared code from losing
ownership and feature boundaries from blurring.

---

## Decision

The application shall follow a single monorepo structure — no package extraction. At ForgeApp's
POC/MVP scope (9 small features, one local developer/team), package extraction overhead is not
justified; this may be revisited if the app grows substantially.

## Module Boundaries

### app/ and config/

Application composition, DI wiring, and cross-cutting configuration (routing, theme). Must not
contain business logic or feature-specific code.

### core/

Shared technical infrastructure (errors, logging, persistence boundary, validation) consumed by
multiple features. Must not contain business logic, UI, or feature-specific code.

### features/

Each subdirectory is a self-contained feature module owning its own `presentation/`,
`application/`, `domain/`, and `data/` layers. Feature modules must not import from other feature
modules directly — cross-feature communication goes through a public repository interface (e.g.
`schedule` reads plan info through `PlansRepository`, not `plans`' internals).

### gen/

Code generated by `build_runner` (generated Drift code). Must not be edited manually.

---

## Cross-Domain Communication

Features communicate only through:

- Shared domain services exposed from `core/`
- Navigation via `go_router` (ADR-003)
- A feature's own public repository interface, consumed by another feature

Direct imports across feature boundaries are prohibited.

---

## Prohibited

- `schedule` importing `plans`' internal implementation directly
- `workout` depending on `history`'s internal implementation
- Business logic inside `core/`, `config/`, or `app/`
- Manual modification of generated files

---

## Alternatives Considered

### Package Extraction from Day One

Rejected — high setup overhead not justified for a 9-feature POC codebase.

### Layer-First Structure (`screens/`, `services/`, `repositories/` at root)

Rejected — fragments business capabilities and conflicts with ADR-001's feature-first
architecture.

---

## Consequences

### Positive

- Clear domain ownership from the start, appropriately lightweight for POC scale

### Negative

- Requires discipline to keep `core/`, `config/`, and `app/` free of business logic
