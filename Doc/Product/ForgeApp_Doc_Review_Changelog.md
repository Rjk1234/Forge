# ForgeApp Documentation — Review & Fix Changelog
*2026-09-05, following the product-owner clarification session*

This review checked all six ForgeApp documents for build-readiness: are requirements complete, mutually consistent, and free of scope drift, given the clarified decisions (Drift-only local architecture, static demo login, no cloud/auth backend, and the specific answers on completion criteria, cancel behavior, scheduling, exercise types, timer behavior, catalogue ownership, and the profile screen). Two items remain deliberately open pending a future brainstorming session — the Personal Best metric definition and app-backgrounded timer behavior — and are flagged as DEFERRED (not resolved, not deleted) in every document that touches them.

## What was found
The single biggest issue was an unresolved architecture conflict: the BRD, PRD, and Business Discovery Doc (the current, correct baseline) described a fully offline app using local Drift storage and a static demo login, while the SDS, Screen Flow/Use Case Inventory, and User Stories still fully specified a Firebase Authentication + Cloud Firestore, online-first architecture — including real registration, login, and password-reset screens that no longer exist. That mismatch has now been resolved everywhere: all seven documents consistently describe the local-only, no-network architecture, with no lingering "offline banner"/"authenticated session" language left over from the old design.

Beyond the architecture fix, each document had a mix of unresolved open questions (from the earlier clarification round) and a few real gaps — most notably, none of them described the newly-approved editable Profile/Account screen, several implied an "Incomplete workout" saved state that contradicts the confirmed always-discard-on-cancel rule, and none consistently captured the exercise-type flag (weighted/time-based/bodyweight), mm:ss duration convention, weekly one-plan-per-day scheduling cap, or auto-start/skippable rest timer. All of these are now fixed and cross-checked for consistency across documents.

## Verified after the fixes
A cross-document consistency pass confirmed all seven documents now agree on: the local-only architecture, the exact 4 profile fields, the completion definition, the always-discard-on-cancel rule, weekly/one-plan-per-day scheduling, the three exercise types with mm:ss duration, the auto-start/skippable rest timer, the fixed exercise catalogue, and — importantly — that the Personal Best metric and app-backgrounded timer behavior are consistently marked **deferred** everywhere, not silently resolved in one document and left open in another. One inconsistency was caught and fixed during this pass (8 leftover "offline" rows in the Screen Flow Inventory that had already been cleaned up in User Stories).

## What's still genuinely open (by design, not oversight)
- **Personal Best metric definition** — heaviest weight / highest reps / highest volume / longest duration (or a combination) — deferred to a future brainstorming session.
- **App-backgrounded timer behavior** — pause-and-resume vs. wall-clock catch-up vs. end-session — deferred to a future brainstorming session.
- A handful of narrower items the clarification round didn't touch were left open rather than guessed at (noted individually inside each document): e.g., which historical record fields can be edited after the fact (PD-003), and local reminder/notification behavior for scheduled workouts.

## Assessment: are the documents build-ready now?
Yes, for the resolved scope. All in-scope functional areas now have consistent, non-contradictory requirements across business, product, design, and story levels, and the documents no longer describe a cloud architecture the app doesn't have. The two explicitly deferred items (Personal Best metric, backgrounded-timer behavior) are the only remaining gaps, and they're now impossible to miss — every document that touches them says so in the same words. Recommend resolving those two in a short follow-up session before the corresponding screens (Personal Bests, Active Workout timer) go into detailed UI/dev work; everything else can proceed.
